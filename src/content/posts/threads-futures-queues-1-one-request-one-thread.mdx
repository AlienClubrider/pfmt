## What a thread is

Your Java code is a list of instructions. A <dfn>thread</dfn> is one worker walking through those instructions, one line at a time.

Each thread has its own *bookmark* (which line it is on) and its own small notepad for local variables and method calls. That notepad is called the <dfn>stack</dfn>. All threads share the same big storage room, the <dfn>heap</dfn>, where your objects live.

A Java program can have many threads at once. That is how one JVM serves hundreds of users at the same time: hundreds of workers, each walking through the same code with different data.

<aside class="callout analogy">
<p class="callout-title">In the kitchen</p>
<p>Think of a restaurant kitchen. Each <strong>cook</strong> is a thread. Every cook follows the same recipe book (your code), but each one is working on a different <strong>order ticket</strong> (a request), and keeps their own place in the recipe.</p>
<p>We will use this kitchen all through the book.</p>
</aside>

## Cores run threads, a few at a time

The CPU has a small number of <dfn>cores</dfn>. A core can run one thread at a time. A laptop might have 8 or more cores; a service container often gets 2 to 8.

So how can 200 threads run on 4 cores? Two reasons.

1. The operating system takes turns. It runs a thread for a short slice of time, then swaps in another. This swap is a <dfn>context switch</dfn>.
2. Most threads in a web service are not running at all. They are asleep, waiting for the database or another service to answer. A sleeping thread does not need a core.

## One request, one thread

A normal Spring Boot web app (Spring MVC) runs inside an embedded **Tomcat** server. Tomcat keeps a group of ready threads, a <dfn>thread pool</dfn>. Their names look like `http-nio-8080-exec-1`, `exec-2`, and so on.

When a request arrives, Tomcat hands it to one free thread. That thread runs your whole call stack: filter, controller, service, repository. It stays with that request until the response is written. Then it goes back to the pool for the next request.

This is called <dfn>thread-per-request</dfn>. It is why plain Spring code is easy to read: everything for one request happens top to bottom, on one thread.

<p class="code-title">OrderController.java</p>

```java
@RestController
@RequestMapping("/orders")
class OrderController {

    private static final Logger log =
            LoggerFactory.getLogger(OrderController.class);

    private final OrderService orders;

    OrderController(OrderService orders) {
        this.orders = orders;
    }

    @GetMapping("/{id}")
    OrderView get(@PathVariable long id) {
        log.info("on thread {}", Thread.currentThread().getName());
        return orders.find(id); // this thread waits for the DB here
    }
}
```

<p class="code-title">log output</p>

```text
INFO [nio-8080-exec-3] c.e.orders.OrderController : on thread http-nio-8080-exec-3
INFO [nio-8080-exec-7] c.e.orders.OrderController : on thread http-nio-8080-exec-7
```

Two requests, two different threads. Notice that Spring's default log pattern shows the thread name in brackets (shortened). That bracket is your first clue when reading logs from concurrent code.

## Tomcat's pool has a size

Tomcat does not create a new thread for every request. It reuses a fixed set. By default the pool grows up to **200 threads**. These are the settings that matter, with their Spring Boot defaults:

<p class="code-title">application.yaml (defaults shown)</p>

```yaml
server:
  tomcat:
    threads:
      max: 200          # most requests handled at the same time
      min-spare: 10     # threads kept alive even when quiet
    max-connections: 8192  # open connections Tomcat will hold
    accept-count: 100      # OS queue once max-connections is hit
```

The key number is `threads.max`. With 200 threads, **at most 200 requests can be in progress at once**. Request number 201 is accepted on a connection, but it waits until one of the 200 threads is free.

So a pool is two things at once: a set of workers, and a *limit*. You will see this idea again and again in this book. Chapter 2 is all about it.

## Why the number of threads matters

If threads are mostly asleep, why not just set `threads.max` to 5,000? Because every thread has a cost, even a sleeping one.

### Memory

Each regular Java thread is a real operating system thread. Each one gets its own stack. On 64-bit Linux the JVM reserves up to **1 MB** per stack by default (the `-Xss` setting). Only the pages actually used are backed by RAM, so real use is usually smaller, but it adds up: thousands of threads can mean gigabytes of reserved memory plus kernel bookkeeping.

### Context switching

When many threads are ready to run at once, the OS spends more time swapping them on and off the cores. Each swap is cheap (microseconds), but at thousands of swaps per second per core it shows up as wasted CPU, and the CPU caches keep going cold.

### The next bottleneck

More threads also means more requests hitting the *next* limit at once. A very common one: the database connection pool. HikariCP, Spring Boot's default, allows **10 connections** unless you change `spring.datasource.hikari.maximum-pool-size`. 200 Tomcat threads sharing 10 connections means up to 190 threads just waiting for a connection.

<aside class="callout why">
<p class="callout-title">Why it matters</p>
<p>Thread count is your service's <strong>concurrency limit</strong>: how many things it can have in progress at once. Too few threads and requests queue up even though the CPU is idle. Too many and you burn memory and CPU on bookkeeping, and you overload whatever is downstream. Your team watches thread count because it tells you, at a glance, how close the service is to that limit.</p>
</aside>

<aside class="callout watch">
<p class="callout-title">Watch out</p>
<p>Raising <code>server.tomcat.threads.max</code> rarely fixes a slow service. If threads are all stuck waiting on a slow database, more threads just means more waiting, and a bigger pile-up when the database recovers. First find <em>what</em> they are waiting on (a thread dump tells you, below).</p>
</aside>

## Seeing your threads

You can look at every thread in a running JVM. Three ways, from quickest to most detailed:

- **Metric**: Spring Boot Actuator with Micrometer publishes `jvm.threads.live` (all threads), `jvm.threads.peak` and `jvm.threads.states` (how many are runnable, waiting, blocked). Chapter 7 builds a dashboard from these.
- **Endpoint**: `GET /actuator/threaddump`, if you have exposed it.
- **Command line**: `jcmd <pid> Thread.print` prints a thread dump.

A thread dump is a list of every thread with its stack. Here is one Tomcat thread, waiting on Postgres:

<p class="code-title">thread dump (trimmed)</p>

```text
"http-nio-8080-exec-3" #52 daemon prio=5 os_prio=0 tid=… nid=…
   java.lang.Thread.State: RUNNABLE
	at sun.nio.ch.SocketDispatcher.read0(Native Method)
	at sun.nio.ch.NioSocketImpl.read(NioSocketImpl.java:…)
	at org.postgresql.core.PGStream.receiveChar(PGStream.java:…)
	at org.postgresql.jdbc.PgPreparedStatement.executeQuery(…)
	at com.example.orders.OrderRepository.findById(…)
	at com.example.orders.OrderService.find(…)
	at com.example.orders.OrderController.get(…)
```

Read it bottom-up: controller called service, service called repository, repository is reading from the database socket. Odd but true: a thread blocked on a socket read often shows as `RUNNABLE`, not `WAITING`, because it is inside native code. Look at the top frames to see what it is really doing.

<p class="callout-title">Recap</p>
<ol>
<li>A thread is a worker walking through your code. In Spring MVC each request gets one Tomcat thread, top to bottom.</li>
<li>Tomcat's pool (200 threads by default) is also a limit: at most that many requests in progress at once.</li>
<li>Threads cost memory and context switches even when asleep, so thread count is a number to watch, not to max out.</li>
</ol>
</aside>
