## 1. Blocking inside the pool

You met this trap in [Chapter 4](../threads-futures-queues-4-completablefuture-read-slowly/#the-common-pool-trap). Here is what it does to a busy service.

When you call `supplyAsync(() -> …)` with no second argument, the task runs on the <dfn>common ForkJoinPool</dfn>. The whole JVM shares that one pool: parallel streams, some libraries, and every other `supplyAsync` without an executor.

Its size is the number of CPU cores minus one. On an 8-core pod that is just **7 threads**. It was built for short bursts of CPU work.

Put a slow HTTP call in it and the thread just stands there waiting. Seven slow calls and the pool is full of waiting threads. Everything else that uses it now waits in line.

<p class="code-title">Don't: blocking call on the common pool</p>

```java
// No executor, so this runs on the shared common pool.
var price = CompletableFuture.supplyAsync(
    () -> pricingClient.fetch(sku));   // blocks ~300 ms
```

The fix is to give blocking work its **own** pool, sized for waiting, and to pass it in every time:

<p class="code-title">PricingExecutorConfig.java</p>

```java
@Configuration
class PricingExecutorConfig {

    @Bean
    ThreadPoolTaskExecutor pricingExecutor() {
        var ex = new ThreadPoolTaskExecutor();
        ex.setThreadNamePrefix("pricing-"); // (1)
        ex.setCorePoolSize(32);
        ex.setMaxPoolSize(32);
        ex.setQueueCapacity(200); // (2)
        return ex;
    }
}
```

<ol class="code-notes">
<li>A clear name shows up in logs and thread dumps, so you can tell who owns a stuck thread.</li>
<li>A bounded queue. The next section explains why.</li>
</ol>

<p class="code-title">Do: pass the executor</p>

```java
var price = CompletableFuture.supplyAsync(
    () -> pricingClient.fetch(sku), pricingExecutor);
```

Now a slow pricing service can fill only the `pricing-` threads. The rest of the app keeps going. [Chapter 6](../threads-futures-queues-6-the-readable-way-virtual-threads/) shows the other way out: virtual threads, where waiting is cheap.

## 2. Unbounded pools and queues

<dfn>Unbounded</dfn> means "no limit". There are two kinds, and both hurt.

- **Unbounded threads.** `Executors.newCachedThreadPool()` makes a new thread whenever none is free. In a traffic spike you get thousands of platform threads. Each one reserves stack memory, and the CPU spends its time switching between them.
- **Unbounded queue.** `Executors.newFixedThreadPool(n)` has a fixed number of threads but a queue with no end. Work is never refused. It just waits longer and longer, and every waiting task holds memory.

Spring Boot's default executor (the one behind `@Async` when virtual threads are off) starts 8 core threads. Unless you set `queue-capacity`, its queue is unbounded.

That has a sneaky side effect. A `ThreadPoolTaskExecutor` only adds threads beyond its core size when the queue is *full*. An endless queue is never full, so `max-size` never kicks in.

Give the default executor real limits in `application.yml`:

<p class="code-title">application.yml</p>

```yaml
spring:
  task:
    execution:
      pool:
        core-size: 16
        max-size: 32
        queue-capacity: 500
```

With a bounded queue, something must happen when it is full. That is the <dfn>rejection policy</dfn>. The default throws a `TaskRejectedException`, which is the "Sorry, we're full" from Chapter 2.

A gentler choice is `CallerRunsPolicy`: the thread that tried to submit the task runs it itself. That slows the caller down, which is exactly the backpressure you want.

```java
ex.setRejectedExecutionHandler(
    new ThreadPoolExecutor.CallerRunsPolicy());
```

## 3. Lost exceptions

A `CompletableFuture` keeps its exception inside itself. Nothing is thrown or logged unless someone calls `join()` or `get()`, or adds a handler like `exceptionally` or `whenComplete`.

So a "fire and forget" task can fail every time, and the logs stay clean.

<div class="compare">
<div>
<p class="compare-label bad">Failure vanishes</p>

```java
CompletableFuture.runAsync(
    () -> audit.record(order),
    auditExecutor);
```

</div>
<div>
<p class="compare-label good">Failure is logged</p>

```java
CompletableFuture.runAsync(
    () -> audit.record(order),
    auditExecutor)
  .whenComplete((ok, ex) -> {
      if (ex != null) log.error(
          "Audit failed {}", order.id(), ex);
  });
```

</div>
</div>

`@Async` methods have the same trap. If the method returns `void`, an exception goes to Spring's `AsyncUncaughtExceptionHandler`, which by default only logs it. If it returns a `CompletableFuture`, the exception sits inside that future until someone looks.

## 4. Starvation and deadlock

<dfn>Starvation</dfn> means a task is ready to run but never gets a thread. <dfn>Deadlock</dfn> is the worst case: tasks wait for each other in a circle, and nothing ever moves.

The classic way to get there: a task running *in* a pool submits a child task *to the same pool*, then waits for it with `join()`. If every thread does that at once, every thread waits for a child stuck in the queue behind it.

<p class="code-title">Don't: wait on your own pool</p>

```java
var report = CompletableFuture.supplyAsync(() -> {
    var lines = CompletableFuture
        .supplyAsync(() -> loadLines(id), pool)
        .join();   // waits for a thread from its own pool
    return new Report(lines);
}, pool);
```

Fixes, best first:

- **Don't block inside a stage.** Chain with `thenCompose` instead of calling `join()` inside the lambda.
- **Use separate pools** for the outer and the inner work.
- **Use virtual threads**, where waiting doesn't hold a scarce pool thread ([Chapter 6](../threads-futures-queues-6-the-readable-way-virtual-threads/)).

<p class="code-title">Do: compose, don't join</p>

```java
var report = CompletableFuture
    .supplyAsync(() -> loadHeader(id), pool)
    .thenCompose(h -> CompletableFuture
        .supplyAsync(() -> loadLines(id), pool)
        .thenApply(lines -> new Report(h, lines)));
```

## 5. Lost MDC and security context

Spring keeps some per-request data in a <dfn>ThreadLocal</dfn>: a variable that belongs to *one thread*. You rely on two of them every day:

- The logging **MDC**, which puts the trace id on every log line.
- The **SecurityContext**, which knows who the current user is.

When your code hops to another thread, those values stay behind. Log lines from the async task have no trace id, and `SecurityContextHolder.getContext()` comes back empty.

The fix is a <dfn>TaskDecorator</dfn>: a small wrapper that Spring runs around every task the executor accepts. It copies the values over before the task and cleans up after.

Spring Framework 6.1+ ships `ContextPropagatingTaskDecorator`. It uses the Micrometer context-propagation library (add `io.micrometer:context-propagation`), so tracing context and MDC follow the task:

<p class="code-title">ContextConfig.java</p>

```java
@Bean
TaskDecorator contextPropagatingTaskDecorator() {
    return new ContextPropagatingTaskDecorator();
}
```

On Spring Boot 4.1 and later you can skip the bean and set one property instead:

<p class="code-title">application.properties</p>

```properties
spring.task.execution.propagate-context=true
```

- Spring Boot applies `TaskDecorator` beans to the executor it auto-configures.
- For your own pools, call `ex.setTaskDecorator(…)` on each `ThreadPoolTaskExecutor`.
- For the logged-in user, Spring Security has `DelegatingSecurityContextAsyncTaskExecutor`, which wraps an executor and carries the `SecurityContext` across.

A decorator only helps tasks that go *through* that executor. A `supplyAsync` with no executor lands on the common pool and gets nothing. One more reason to always pass the executor.

## 6. No timeouts

`join()` and `get()` with no arguments wait **forever**. If a downstream service hangs, your request thread hangs with it.

Hang enough of them and Tomcat's 200 request threads are used up. Then the whole service stops answering, even requests that never touch the slow service.

<p class="code-title">PriceService.java</p>

```java
var price = CompletableFuture
    .supplyAsync(() -> pricingClient.fetch(sku),
        pricingExecutor)
    .completeOnTimeout(Price.unknown(), // (1)
        800, MILLISECONDS);

// or, to fail instead of falling back:
// .orTimeout(800, MILLISECONDS) // (2)
```

<ol class="code-notes">
<li>After 800&nbsp;ms the future completes with a fallback value.</li>
<li>After 800&nbsp;ms the future fails with a <code>TimeoutException</code>.</li>
</ol>

Put timeouts in two places. On the **future**, so the caller stops waiting. And on the **client** (HTTP connect and read timeouts, a JDBC query timeout), so the thread doing the work also lets go.

<aside class="callout watch">
<p class="callout-title">Watch out</p>
<p><code>orTimeout</code> and <code>completeOnTimeout</code> finish the <em>future</em>. They don't stop the work. The pool thread stays inside <code>pricingClient.fetch</code> until that call returns.</p>
<p><code>cancel(true)</code> on a <code>CompletableFuture</code> doesn't interrupt the thread either. Only a timeout on the client itself frees that thread.</p>
</aside>

## A code review checklist

When you read async code at work, ask these six questions:

1. Does every `supplyAsync` / `runAsync` pass an executor?
2. Does every pool limit both its threads *and* its queue?
3. Does every future end in a `join`, a handler, or a log line?
4. Does any task wait on another task in the same pool?
5. Does the executor carry MDC and the security context?
6. Does every remote call have a timeout?

<aside class="callout why">
<p class="callout-title">Why it matters</p>
<p>At thousands of requests per second, a pitfall doesn't fail one request. It fails all of them together.</p>
<p>One slow dependency, one shared pool and no timeout add up to a full outage. Separate bounded pools and a timeout on every remote call turn "everything is down" into "one feature is slow".</p>
</aside>

<aside class="callout recap">
<p class="callout-title">Recap</p>
<ol>
<li>Never block on the common pool. Give blocking work its own bounded pool and always pass it in.</li>
<li>Every future needs an ending (a join, a handler or a log) and every remote call needs a timeout.</li>
<li>Context doesn't follow you to another thread by itself, and a pool must never wait on itself.</li>
</ol>
</aside>
