During all that amber time, the thread is parked. The CPU core is free to run other threads. That is why a pool of 200 threads works on 4 cores (Chapter 1).

But it also tells you where to look for speed. Making the green part faster barely matters. Shrinking or overlapping the amber part is where the wins are.

<aside class="callout analogy">
<p class="callout-title">In the kitchen</p>
<p>A cook puts a roast in the oven for 40 minutes. If the cook stands and stares at the oven, one dish takes 40 minutes of the cook's time. If the cook puts the roast in, starts the soup, and chops the salad while both cook, the whole meal is ready when the <em>slowest</em> thing is done. Same cook, same oven. Far less standing around.</p>
</aside>

## The slowest call, not the sum

Say the home page needs three things that don't depend on each other: the user's **profile** (120 ms), their recent **orders** (200 ms), and **recommendations** (80 ms).

Called one after another, the wait times add up: 120 + 200 + 80 = 400 ms. Started at the same time, the waits overlap, and you are done when the slowest one is done: 200 ms.

<p class="code-title">HomePageService.java</p>

```java
HomePage load(long userId) {
    var profile = supplyAsync(
        () -> profiles.get(userId), ioPool);
    var orders = supplyAsync(
        () -> orderClient.recent(userId), ioPool);
    var recs = supplyAsync(
        () -> recClient.forUser(userId), ioPool);

    return new HomePage(profile.join(),
                        orders.join(), recs.join());
}
```

</div>

(`supplyAsync` is statically imported from `CompletableFuture`; `ioPool` is a bounded executor like the one in [Chapter 2](../threads-futures-queues-2-pools-and-queues/#springs-async-and-its-executor).)

This only works for calls that are **independent**. If you need the profile's region before you can ask for recommendations, those two have to stay in order. Finding which calls are independent is the first step in reading or writing any concurrent code.

## Parallel I/O vs parallel CPU

There are two very different kinds of "parallel", and they get mixed up a lot.

- **I/O-bound** work (HTTP calls, DB queries, reading queues) is mostly waiting. You can overlap far more of it than you have cores, because waiting threads use no CPU. This is the kind that makes business services fast.
- **CPU-bound** work (parsing a huge file, image resizing, heavy math) keeps a core busy the whole time. Splitting it helps only up to the number of cores. 4 cores can do 4 CPU tasks at once; the 5th waits.

Most code you'll see at work with `CompletableFuture` is the first kind: fan out a few remote calls, then combine.

## The math of "thousands per second"

Here is the one formula worth remembering. It is called <dfn>Little's law</dfn>, and in plain words it says:

<p class="formula">in progress at once = arrivals per second × seconds each one takes</p>

In the kitchen: if 60 orders come in per hour and each spends 10 minutes being cooked, then on average 60 × (10/60) = **10 orders are in the kitchen at any moment**. If every order needs a cook for its whole 10 minutes, you need about 10 cooks.

For a service: one instance gets **800 requests per second**. Five instances behind a load balancer make that 4,000 per second, "thousands per second". Each request holds a Tomcat thread for its whole duration. So:

<aside class="callout why">
<p class="callout-title">Why it's fast</p>
<ul>
<li><strong>Waits overlap.</strong> Three 100 ms waits done together take 100 ms, not 300.</li>
<li><strong>Threads are freed sooner.</strong> A request that finishes in half the time holds its thread half as long, so the same pool serves twice the traffic (Little's law).</li>
<li><strong>The CPU never stands still.</strong> While one thread waits on the network, the core runs another one's green slice.</li>
</ul>
</aside>

<aside class="callout watch">
<p class="callout-title">Watch out</p>
<p>The parallel version uses <em>more</em> threads per request, not fewer. In the example each request now also has 3 calls running on the I/O pool. By Little's law that pool has about 800 × (0.12 + 0.2 + 0.08) = <strong>320 tasks in progress</strong>. So Tomcat needs fewer threads, but the I/O pool needs a lot. Size it, bound it, and watch it, or you have just moved the pile-up. (Chapter 6 shows how virtual threads make this cost almost disappear.)</p>
</aside>

<aside class="callout recap">
<p class="callout-title">Recap</p>
<ol>
<li>Most request time is waiting on I/O, not CPU work. Speed comes from overlapping the waits.</li>
<li>Independent calls done at once take as long as the slowest one, not the sum.</li>
<li>Little's law: in progress at once = rate × time. Halve the time and you halve the threads you need.</li>
</ol>
</aside>
