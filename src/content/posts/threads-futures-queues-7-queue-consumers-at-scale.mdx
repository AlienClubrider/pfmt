<aside class="callout analogy">
<p class="callout-title">In the kitchen</p>
<p>Delivery drivers line up outside the back door. That line is the <dfn>message broker</dfn>: Kafka, RabbitMQ or SQS. The drivers don't barge in. The kitchen opens the door and takes a few boxes when it has room.</p>
<p>Just inside the door is a small shelf for boxes taken in but not yet unpacked. That is the <dfn>prefetch</dfn> buffer. A fixed number of cooks unpack boxes from the shelf, one each at a time. That is the listener <dfn>concurrency</dfn>.</p>
<p>If the cooks slow down, the shelf stays full, the door stays shut, and the line outside grows. The kitchen is protected. The growing line is called <dfn>lag</dfn>, and it is the number you watch.</p>
</aside>

## How a listener pulls work

A web request is *pushed* at you: the caller decides when it arrives. A queue listener *pulls*: it asks the broker for more only when it is ready.

That one difference gives you backpressure for free. Each listener thread runs a simple loop: fetch a few messages, process them one by one, confirm them (ack or commit), fetch again.

<ol class="step-notes">
<li>Messages wait in the broker. Three listener threads are idle and ask for work.</li>
<li>The container fetches a batch into memory: Kafka's <code>max.poll.records</code>, Rabbit's <code>prefetch</code>, SQS's <code>maxMessagesPerPoll</code>.</li>
<li>Each listener thread takes one message and processes it. When the buffer runs low, the container fetches again.</li>
<li>The database slows down. The listeners take longer, the buffer stays full, and nothing new is fetched. Messages pile up in the broker, not in your heap. That pile-up is lag.</li>
</ol>

## The knobs, broker by broker

Every broker has the same two dials. **Concurrency**: how many messages are processed at once. **Batch size**: how many are pulled into memory ahead of time.

<p class="code-title">Listeners.java</p>

```java
@KafkaListener(topics = "orders", concurrency = "6")
void onOrder(OrderEvent event) { … }

@RabbitListener(queues = "invoices", concurrency = "4-8")
void onInvoice(InvoiceMessage msg) { … }

@SqsListener(value = "shipments",
        maxConcurrentMessages = "20",
        maxMessagesPerPoll = "10")
void onShipment(ShipmentMessage msg) { … }
```

Or set defaults for every listener in `application.yml`:

<p class="code-title">application.yml</p>

```yaml
spring:
  kafka:
    listener:
      concurrency: 6
    consumer:
      max-poll-records: 100
  rabbitmq:
    listener:
      simple:
        concurrency: 4
        max-concurrency: 8
        prefetch: 20
```

### Kafka: partitions are the ceiling

In Kafka, one partition is read by exactly one consumer in a group at a time. Spring's `concurrency = "6"` starts 6 consumers, each with its own thread. More consumers than partitions just leaves some of them with nothing to do.

Messages in one partition are processed in order, by one thread. That's a feature: events for the same order id stay in sequence. It is also why you can't fix a slow Kafka consumer by just adding threads.

### Kafka: the five-minute rule

Kafka expects each consumer to call `poll()` again within `max.poll.interval.ms` (default 5 minutes). If one batch of 500 records takes longer than that, Kafka decides the consumer is dead and moves its partitions to someone else. That's a <dfn>rebalance</dfn>, and the slow batch may be processed twice.

If each message is slow, lower `max-poll-records`. Don't just raise the timeout.

### RabbitMQ: prefetch hoards messages

With a prefetch of 250 and 4 consumers, one pod can hold 1,000 unacknowledged messages. If that pod is slow, those messages wait there while other pods sit idle. For slow messages, a small prefetch (1 to 20) spreads work more evenly.

## Don't break the backpressure

The pull loop only protects you if the listener method actually *finishes the work* before it returns. A common "speed-up" breaks that:

<div class="compare">
<div>
<p class="compare-label bad">Hands off and returns</p>

```java
@KafkaListener(topics = "orders")
void onOrder(OrderEvent e) {
  // returns at once; offset is
  // committed before work is done
  CompletableFuture.runAsync(
      () -> handle(e), pool);
}
```

</div>
<div>
<p class="compare-label good">Does the work in the listener</p>

```java
@KafkaListener(topics = "orders",
               concurrency = "6")
void onOrder(OrderEvent e) {
  handle(e); // blocks this thread;
             // that is the point
}
```

</div>
</div>

In the left version the listener grabs messages as fast as the broker can send them. They pile up in `pool`'s queue, in your heap. The broker thinks they are done, so a crash loses them. Lag looks perfect while the service drowns.

If one message needs several calls, make those calls in parallel *inside* the listener and wait for them before returning (the executor version from [Chapter 6](../threads-futures-queues-6-the-readable-way-virtual-threads/#parallel-calls-written-plainly)).

## Sizing: how many at once?

Use Little's law from [Chapter 3](../threads-futures-queues-3-why-its-fast/): **messages in flight = arrival rate × time per message**.

1. Peak rate: **1,500 messages/second** (from your broker's metrics).
2. Time per message: **40 ms** on average (from the listener timer below).
3. In flight: 1,500 × 0.040 = **60** messages being processed at any moment.
4. Add headroom for spikes and slow moments, say 1.5×: about **90**.
5. Spread over 6 pods: **15 per pod**. For Kafka, that also means at least 90 partitions, or fewer, faster consumers.

These are example numbers. Plug in your own.

Then check what each message *touches*. If every message holds a database connection, 15 consumers per pod needs at least 15 connections in that pod's pool (HikariCP's default is 10). The smallest limit along the path is your real concurrency.

<aside class="callout why">
<p class="callout-title">Why it matters</p>
<p>Too few consumers and lag grows all day. Too many and you overload the database, and adding threads makes things <em>slower</em>.</p>
<p>The right number comes from measuring rate and time per message, not from guessing. That is why the next section is about watching.</p>
</aside>

## Watching it: the metrics that matter

Spring Boot Actuator with Micrometer publishes most of what you need. Expose it, and send it to Prometheus, Datadog or whatever your team uses:

<p class="code-title">application.properties</p>

```properties
management.endpoints.web.exposure.include=health,metrics,prometheus,threaddump
# Tomcat thread metrics are off unless this is on:
server.tomcat.mbeanregistry.enabled=true
```

Boot binds the `executor.*` metrics for every `ThreadPoolTaskExecutor` bean it can see. A raw `ExecutorService` you built yourself is invisible unless you wrap it with Micrometer's `ExecutorServiceMetrics.monitor(…)`. Another reason to build pools as Spring beans with clear names.

<aside class="callout watch">
<p class="callout-title">Watch out</p>
<p><strong>Virtual threads are not in <code>jvm.threads.live</code>.</strong> That metric counts platform threads only. With virtual threads on, a flat thread graph doesn't mean low concurrency. Watch in-flight work instead: Tomcat busy count, semaphore permits in use, listener timers, and lag.</p>
<p>Also, lag alone can lie. Lag of 10,000 is fine if it drains in 5 seconds and terrible if it has been there for an hour. Watch the <em>age</em> of the oldest message where your broker reports it.</p>
</aside>

### Thread dumps: a photo of every thread

When something is stuck, a <dfn>thread dump</dfn> shows what every thread is doing right now. Take two or three, ten seconds apart. Threads stuck on the same line in all of them are your problem.

<p class="code-title">Taking a dump</p>

```bash
# platform threads, over HTTP (Actuator)
curl -s localhost:8080/actuator/threaddump -H 'Accept: text/plain'

# platform threads, on the box
jcmd <pid> Thread.print

# includes virtual threads (Java 21+)
jcmd <pid> Thread.dump_to_file -format=json /tmp/threads.json

# quick summary: how many threads in each state
jcmd <pid> Thread.print | grep 'Thread.State' | sort | uniq -c
```

What a stuck pricing thread looks like (trimmed):

```text
"pricing-17" #93 prio=5 os_prio=0 runnable
   java.lang.Thread.State: RUNNABLE
    at sun.nio.ch.Net.poll(Native Method)
    at sun.nio.ch.NioSocketImpl.timedRead(...)
    at java.net.Socket$SocketInputStream.read(...)
    ...
    at com.acme.pricing.PricingClient.fetch(PricingClient.java:41)
```

Read it bottom-up for *your* code (`PricingClient.fetch`, line 41), then top-down for *what it is waiting on* (a socket read). If 32 of 32 `pricing-` threads look like this, the pricing service is slow, and you're missing a read timeout.

Name your threads (`setThreadNamePrefix`) and a dump reads like a list of owners. With names like `pool-7-thread-3` it reads like a puzzle.

A checklist for each service that pulls from a queue:

1. **Threads:** `jvm.threads.live` is flat over a day. Alert on a steady climb.
2. **Pools:** `executor.active` stays below max most of the time, and `executor.queued` stays near zero.
3. **Lag:** drains after every spike. Alert when lag or oldest-message age keeps growing for several minutes.
4. **Time per message:** p99 from the listener timer. A jump here usually explains the other three.
5. **Errors:** listener failure count, dead-letter queue size, and Kafka rebalances in the logs.
6. **Downstream:** DB pool usage (`hikaricp.connections.active`, `hikaricp.connections.pending`). The real limit often lives here.

<aside class="callout recap">
<p class="callout-title">Recap</p>
<ol>
<li>Listeners pull: concurrency caps work in progress, and prefetch / poll size caps what is held in memory. Kafka can't go past its partition count.</li>
<li>Size with rate × time per message, then check the smallest downstream limit. Never hand off and return.</li>
<li>Watch four things: threads, pool active/queued, lag (and its age), and time per message. Name your threads so dumps make sense.</li>
</ol>
