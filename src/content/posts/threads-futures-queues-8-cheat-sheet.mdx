<aside class="callout analogy">
<p class="callout-title">In the kitchen</p>
<p>A new cook walks into a busy kitchen. Before touching anything they ask five things. Where do tickets come in? Who cooks them? What happens to each dish? Where does it go out, and what if it's burnt? How many can we do at once?</p>
<p>Reading async code is the same five questions.</p>

<ol class="steps">
<li><strong>Find where work leaves the current thread.</strong> Search the class for <code>supplyAsync</code>, <code>runAsync</code>, <code>@Async</code>, <code>.submit(</code>, <code>parallelStream</code>, <code>@KafkaListener</code>, <code>@RabbitListener</code>, <code>@SqsListener</code>. Everything else runs on the caller's thread.</li>
<li><strong>Name the executor for each one.</strong> Is one passed in? Which bean is it, and how many threads and how big a queue does it have? No executor on <code>supplyAsync</code> means the common pool (cores&nbsp;−&nbsp;1 threads). <code>@Async</code> with no name means Spring Boot's <code>applicationTaskExecutor</code>.</li>
<li><strong>Read each chain top to bottom</strong>, saying each method in plain words with the table below. Note any <code>…Async</code> stage, because that is another hop to another thread.</li>
<li><strong>Find where it ends, and what happens when it fails.</strong> Is the future joined, returned to Spring (a controller can return a <code>CompletableFuture</code>), or dropped? Is there an <code>exceptionally</code>/<code>handle</code>, and a timeout? A dropped future with no handler is a silent failure (<a href="../threads-futures-queues-5-pitfalls/#3-lost-exceptions">Chapter 5</a>).</li>
<li><strong>Count the limits along the path.</strong> Pool sizes, queue capacities, semaphores, listener concurrency, partitions, the DB connection pool. The smallest one is how many can really run at once.</li>
</ol>

## CompletableFuture in plain words

Each method, what it means out loud, and how you would write the same thing with virtual threads ([Chapter 6](../threads-futures-queues-6-the-readable-way-virtual-threads/)).

<div class="table-wrap">
<table>
<thead>
<tr><th>Method</th><th>Say it as</th><th>Plain-code version</th></tr>
</thead>
<tbody>
<tr><td><code>supplyAsync(f, ex)</code></td><td>Start <code>f</code> on <code>ex</code>; give me a ticket for the result</td><td><code>exec.submit(f)</code></td></tr>
<tr><td><code>thenApply(f)</code></td><td>…then change the result with <code>f</code></td><td><code>var y = f(x);</code></td></tr>
<tr><td><code>thenCompose(f)</code></td><td>…then start another async step that needs the result</td><td><code>var y = callNext(x);</code></td></tr>
<tr><td><code>thenCombine(b, f)</code></td><td>When this <em>and</em> <code>b</code> are done, merge them</td><td><code>f(a.get(), b.get())</code></td></tr>
<tr><td><code>thenAccept(f)</code></td><td>…then use the result, return nothing</td><td><code>f(x);</code></td></tr>
<tr><td><code>allOf(a, b, c)</code></td><td>Wait until all of them are done</td><td><code>a.get(); b.get(); c.get();</code></td></tr>
<tr><td><code>anyOf(a, b)</code></td><td>Whichever finishes first</td><td><code>exec.invokeAny(tasks)</code></td></tr>
<tr><td><code>exceptionally(f)</code></td><td>If it failed, use <code>f</code> to make a fallback</td><td><code>try \{ … \} catch (…) \{ fallback \}</code></td></tr>
<tr><td><code>handle((r, ex) -&gt; …)</code></td><td>Either way, look at result <em>or</em> error and decide</td><td><code>try/catch</code> that returns in both</td></tr>
<tr><td><code>whenComplete((r, ex) -&gt; …)</code></td><td>Either way, do a side effect (log); result unchanged</td><td><code>finally \{ log… \}</code></td></tr>
<tr><td><code>orTimeout(t)</code></td><td>Fail if not done in <code>t</code></td><td><code>future.get(t, unit)</code></td></tr>
<tr><td><code>completeOnTimeout(v, t)</code></td><td>Use <code>v</code> if not done in <code>t</code></td><td><code>get(t, unit)</code> + catch <code>TimeoutException</code></td></tr>
<tr><td><code>join()</code> / <code>get()</code></td><td>Stop here and wait</td><td><code>future.get()</code></td></tr>
<tr><td><code>…Async</code> versions</td><td>Same, but run the step on an executor (another hop)</td><td>Usually not needed</td></tr>
</tbody>
</table>
</div>

One rule from [Chapter 4](../threads-futures-queues-4-completablefuture-read-slowly/) worth repeating: a stage *without* `Async` runs on whichever thread finished the stage before it, or on the caller if that stage was already done. Don't put slow work there unless you know which thread that is.

<aside class="callout watch">
<p class="callout-title">Watch out</p>
<p>Three red flags to spot in five seconds:</p>
<ul>
<li><code>supplyAsync(…)</code> with <strong>one</strong> argument doing I/O: it's on the common pool.</li>
<li><code>.join()</code> <strong>inside</strong> a lambda that runs on a pool: a starvation or deadlock risk.</li>
<li>A future that is never joined, returned or handled: failures disappear.</li>
</ul>
</aside>

<aside class="callout why">
<p class="callout-title">Why it matters</p>
<p>Most production incidents with async code aren't clever bugs. They're a default nobody looked at: an unbounded queue, a pool of 10 behind 200 request threads, a single scheduler thread. Knowing these numbers turns "it's slow sometimes" into "the Hikari pool is the bottleneck".</p>
</aside>

## Glossary

<dl class="glossary"> <dt>Thread</dt> <dd>One line of execution: the code runs step by step on it. A cook.</dd> <dt>Platform thread</dt> <dd>A Java thread backed by one operating-system thread. Costly, so you keep hundreds, not hundreds of thousands.</dd> <dt>Virtual thread</dt> <dd>A thread managed by the JVM (Java 21+). Cheap; it gives up its carrier while it waits.</dd> <dt>Carrier thread</dt> <dd>A platform thread that runs virtual threads, one at a time.</dd> <dt>Thread pool / executor</dt> <dd>A fixed crew of threads that takes tasks from a queue. <code>ThreadPoolTaskExecutor</code> in Spring.</dd> <dt>Task queue</dt> <dd>Where tasks wait for a free thread. The ticket rail. Should be bounded.</dd> <dt>Common pool</dt> <dd>The JVM-wide <code>ForkJoinPool</code> that <code>supplyAsync</code> uses when you pass no executor. Cores − 1 threads.</dd> <dt>Blocking</dt> <dd>A call that makes the thread wait until it returns, like a socket read or <code>future.get()</code>.</dd> <dt>I/O wait</dt> <dd>Time spent waiting for a network, disk or database, not using the CPU.</dd> <dt>CompletableFuture</dt> <dd>A ticket for a result that may not exist yet, plus a list of steps to run when it does.</dd> <dt>Stage</dt> <dd>One step in a <code>CompletableFuture</code> chain (<code>thenApply</code>, <code>thenCompose</code>, …).</dd> <dt>Latency</dt> <dd>How long one request takes, start to finish.</dd> <dt>Throughput</dt> <dd>How many requests (or messages) are finished per second.</dd> <dt>Little's law</dt> <dd>In flight = rate × time each. 1,000/s × 0.05&nbsp;s = 50 at once.</dd> <dt>Context switch</dt> <dd>The CPU stopping one thread to run another. Cheap once, costly by the million.</dd> <dt>Backpressure</dt> <dd>Slowing down whoever sends work when you are full, instead of piling it up.</dd> <dt>Rejection policy</dt> <dd>What a full pool does with a new task: throw, run it on the caller, or drop it.</dd> <dt>Starvation</dt> <dd>A task that is ready but never gets a thread.</dd> <dt>Deadlock</dt> <dd>Tasks waiting on each other in a circle, so none can move.</dd> <dt>ThreadLocal</dt> <dd>A variable with a separate value per thread. Holds the MDC and the security context.</dd> <dt>MDC</dt> <dd>Mapped Diagnostic Context: the key-values (like trace id) your logger adds to every line.</dd> <dt>TaskDecorator</dt> <dd>A Spring wrapper around each task, used to copy context to the worker thread.</dd> <dt>Semaphore</dt> <dd>A counter of permits. Caps how many callers can be inside a section at once.</dd> <dt>Pinning</dt> <dd>A virtual thread that can't unmount while it waits, so it holds its carrier. Mostly fixed in Java 24+.</dd> <dt>Structured concurrency</dt> <dd>Forking subtasks inside a scope that waits for, and cancels, all of them. Preview until Java 28.</dd> <dt>Listener concurrency</dt> <dd>How many messages a queue consumer processes at once.</dd> <dt>Prefetch / poll size</dt> <dd>How many messages a consumer pulls into memory ahead of processing.</dd> <dt>Partition</dt> <dd>A Kafka topic's unit of order and parallelism. One consumer per partition per group.</dd> <dt>Rebalance</dt> <dd>Kafka moving partitions between consumers, for example when one is too slow to poll.</dd> <dt>Lag</dt> <dd>How far a consumer is behind the newest message. The number to watch.</dd> <dt>Thread dump</dt> <dd>A snapshot of every thread and the line it is on. <code>jcmd &lt;pid&gt; Thread.print</code>.</dd> </dl>

<aside class="callout recap">
<p class="callout-title">Recap</p>
<ol>
<li>Read async code in five steps: where work leaves, who runs it, the chain in plain words, the end and the failure path, and the limits.</li>
<li>Waiting-heavy work on Java 21+: virtual threads plus an explicit limit. CPU work: a small bounded pool. Queue work: listener concurrency.</li>
<li>Know the defaults (200, cores − 1, 8 + unbounded, 500, 250, 10). Most incidents hide in one of them.</li>
</ol>
