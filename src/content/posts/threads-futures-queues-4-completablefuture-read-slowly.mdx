## A box that fills in later

A <dfn>CompletableFuture&lt;T&gt;</dfn> is a box that will hold a `T` later. Right now it may be empty. At some point it gets filled with either a value or an error. That is all it is.

You can do two things with the box:

1. **Wait for it**: `join()` blocks the current thread until the box is filled.
2. **Attach a next step**: "when this box is filled, run this function". The method returns a *new* box for the result of that step.

Attaching steps to boxes, one after another, is what a "chain" is. Each line of a chain is a new box that depends on the box above it.

<aside class="callout analogy">
<p class="callout-title">In the kitchen</p>
<p>At a burger counter you order, pay, and get a <strong>buzzer</strong>. The buzzer is the future: it is not your food, it is a promise of food. You can stand at the counter staring at it (<code>join()</code>), or leave instructions: "when it buzzes, add fries and bring it to table 6" (<code>thenApply</code>). Meanwhile, the counter is free to serve the next person.</p>
</aside>

## Starting work: `supplyAsync`

Most chains begin with `supplyAsync`: "run this function on another thread, and give me a box for its result".

```java
CompletableFuture<Cart> cartF =
        CompletableFuture.supplyAsync(() -> carts.load(cartId), ioPool);
```

The call returns immediately with an empty box. A thread from `ioPool` runs `carts.load` and fills the box later. `runAsync` is the same for work that returns nothing.

Note the second argument, `ioPool`. It is optional, and leaving it out is the most common mistake with this API. More on that in [the common pool trap](#the-common-pool-trap).

A `CompletableFuture` can also come from a library instead: Spring's `@Async` methods ([Chapter 2](../threads-futures-queues-2-pools-and-queues/#springs-async-and-its-executor)), the JDK's `HttpClient.sendAsync`, or `WebClient … .toFuture()`. They all give you the same kind of box.

Every `then…` method also has an `…Async` twin, like `thenApplyAsync`. Same job; the difference is *which thread* runs it. That gets its own section below.

## `thenApply` vs `thenCompose`

This pair confuses everyone once. The rule: look at what your function returns.

- It returns a plain value (`user.name()`)? Use `thenApply`.
- It returns *another future* (an async call)? Use `thenCompose`.

<p class="code-title">the rule in code</p>

```java
// function returns a value: thenApply
CompletableFuture<String> name =
        userF.thenApply(user -> user.name());

// function returns a future: thenCompose
CompletableFuture<Address> address =
        userF.thenCompose(user -> addressClient.lookup(user.id()));

// wrong verb: a box inside a box
CompletableFuture<CompletableFuture<Address>> oops =
        userF.thenApply(user -> addressClient.lookup(user.id()));
```

## Waiting for two, or for many

**Two independent things**: start both, then merge with `thenCombine`. This is the "latency = slowest call" trick from [Chapter 3](../threads-futures-queues-3-why-its-fast/#the-slowest-call-not-the-sum).

```java
var profileF = supplyAsync(() -> profiles.get(id), ioPool);
var ordersF  = supplyAsync(() -> orders.recent(id), ioPool);

CompletableFuture<AccountPage> page =
        profileF.thenCombine(ordersF, AccountPage::new);
```

**A list of things**: start one future per item, wait for all with `allOf`, then read each result. `allOf` gives you a `CompletableFuture<Void>`, so the values come from the original futures. Calling `join()` on them after `allOf` is done does not wait at all.

```java
List<CompletableFuture<Price>> futures = skus.stream()
        .map(sku -> supplyAsync(() -> pricing.price(sku), ioPool))
        .toList();

CompletableFuture.allOf(futures.toArray(CompletableFuture[]::new))
        .join(); // wait for every price

List<Price> prices = futures.stream()
        .map(CompletableFuture::join) // already done, no waiting
        .toList();
```

## When something fails

If a step throws, its box is filled with the error. As Figure 4.1 showed, the error then skips every normal step below until it meets a handler:

```java
CompletableFuture<Quote> quote = pricing.quote(cart)
        .exceptionally(ex -> Quote.unavailable())   // error → value
        .whenComplete((q, ex) -> metrics.record(q)); // look only

CompletableFuture<Quote> same = pricing.quote(cart)
        .handle((q, ex) -> ex == null ? q : Quote.unavailable());
```

Two details that trip people up:

- **The error is often wrapped.** If a step throws inside a chain, later steps see a `CompletionException` with your real exception inside as the *cause*. Check `ex.getCause()` before deciding what went wrong.
- **`join()` vs `get()`**. Both block. `join()` throws an unchecked `CompletionException`; `get()` throws a checked `ExecutionException` (and `InterruptedException`). Same cause inside either way.

<aside class="callout watch">
<p class="callout-title">Watch out</p>
<p>A chain with no <code>exceptionally</code>, <code>handle</code> or <code>join()</code> at the end <strong>swallows its errors</strong>. Nobody looks inside the box, so the exception is never logged. If you see a chain that is started and then dropped (fire and forget), make sure it ends with a handler that at least logs. Chapter 5 has more of these traps.</p>
</aside>

## Which thread runs what

This is the part nobody tells you, and it decides whether a chain is safe. The rules:

<div class="table-wrap">
<table>
<thead>
<tr><th>You wrote</th><th>The function runs on</th></tr>
</thead>
<tbody>
<tr><td><code>supplyAsync(f, pool)</code></td><td>a thread from <code>pool</code></td></tr>
<tr><td><code>supplyAsync(f)</code></td><td><code>ForkJoinPool.commonPool()</code> (see below)</td></tr>
<tr><td><code>thenApply(f)</code> (no Async)</td><td>whichever thread <em>filled the box above</em>; or, if it was already filled, the thread that called <code>thenApply</code></td></tr>
<tr><td><code>thenApplyAsync(f, pool)</code></td><td>a thread from <code>pool</code></td></tr>
<tr><td><code>thenApplyAsync(f)</code></td><td>the common pool</td></tr>
<tr><td><code>join()</code></td><td>blocks the thread that calls it</td></tr>
</tbody>
</table>
</div>

The non-Async steps are the slippery ones: you can't tell from the code which thread runs them. That's fine for quick transforms like `Cart::total`. It's not fine for anything slow or blocking. If a step does I/O, give it an executor: `thenApplyAsync(f, ioPool)`.

## The common pool trap

Leave out the executor (`supplyAsync(f)`, `thenApplyAsync(f)`) and the work runs on `ForkJoinPool.commonPool()`. Three facts about that pool:

1. It is **shared by the whole JVM**: parallel streams, other libraries, every other future without an executor.
2. It is **small**: by default, one thread fewer than the number of CPUs. A 4-CPU container gets 3 threads.
3. It was **designed for CPU work**, not for waiting on HTTP or databases.

So a handful of slow HTTP calls without an executor can block all of its threads, and every other user of the pool stalls behind them.

One more surprise: if the machine has so few CPUs that the common pool would get *fewer than two* threads, `CompletableFuture` doesn't use it at all. It starts a **brand-new thread for every task** instead. On a 1 or 2 CPU container, that is an unbounded number of threads. Your thread count graph will show it.

## Reading a real chain, top to bottom

Here is the kind of code you might meet at work. A checkout page needs the cart's price quote with the customer's loyalty points applied, within 800 ms, or a fallback.

<p class="code-title">CheckoutSummaryService.java</p>

```java
CompletableFuture<CheckoutSummary> summary(long cartId) {
    var pointsF = supplyAsync(                          // (1)
            () -> loyalty.points(cartId), ioPool);

    return supplyAsync(() -> carts.load(cartId), ioPool) // (2)
            .thenCompose(cart -> pricing.quote(cart))    // (3)
            .thenCombine(pointsF, Quote::withPoints)     // (4)
            .thenApply(CheckoutSummary::from)            // (5)
            .orTimeout(800, MILLISECONDS)                // (6)
            .exceptionally(ex -> {                       // (7)
                log.warn("summary failed for {}", cartId, ex);
                return CheckoutSummary.unavailable(cartId);
            });
}
```

<ol class="code-notes">
<li><strong>Starts now.</strong> The loyalty call begins on an <code>ioPool</code> thread the moment <code>summary()</code> is called. It runs in parallel with everything below.</li>
<li><strong>Also starts now</strong>, on another <code>ioPool</code> thread: load the cart. Steps 1 and 2 are the "fan out".</li>
<li><code>thenCompose</code>: once the cart is loaded, ask pricing for a quote. <code>pricing.quote</code> is itself async (returns a future), so this is <code>thenCompose</code>, not <code>thenApply</code>. Runs on the thread that loaded the cart.</li>
<li><code>thenCombine</code>: wait for the quote <em>and</em> the points from step 1, then apply the points. Runs on whichever of the two finished last.</li>
<li><code>thenApply</code>: a quick, pure transform into the response type. Same thread as step 4.</li>
<li><code>orTimeout</code>: if the whole chain above isn't done within 800 ms, fill the box with a <code>TimeoutException</code>. Note: this does <em>not</em> stop the calls that are still running; it only stops waiting for them.</li>
<li><code>exceptionally</code>: any error above (cart, pricing, loyalty or timeout) lands here. Errors from earlier steps arrive wrapped in a <code>CompletionException</code>; the timeout arrives as a plain <code>TimeoutException</code>. Log it and return a fallback, so the caller always gets a value. On a timeout this runs on the JDK's internal timer thread, which is one more reason to keep handlers short.</li>
</ol>

Total time: roughly the slower of "cart then quote" and "points", capped at 800 ms. Without futures it would be cart + quote + points, uncapped.

Here is the routine you just used, as five questions. [Chapter 8](../threads-futures-queues-8-cheat-sheet/#read-async-code-in-five-steps) keeps it on one page for work.

<ol class="steps">
<li><strong>Where does work leave this thread?</strong> Look for <code>supplyAsync</code>, <code>runAsync</code>, <code>@Async</code>, and methods that return a future. Above: steps 1 and 2 (and the pricing client's own async call in step 3). Everything started before something is waited on runs at the same time.</li>
<li><strong>Who runs it?</strong> Name the executor for each start. Above: <code>ioPool</code> every time. No executor means the common pool.</li>
<li><strong>Read the chain in plain words.</strong> One line, one "and when that's done…". <code>thenCompose</code> = another async call; <code>thenCombine</code> / <code>allOf</code> = waiting for things started earlier.</li>
<li><strong>How does it end, and what if it fails?</strong> Find the handler and the timeout, and who receives the box (here: the caller). No handler means silent failures; no timeout means a stuck call holds threads forever. Every <code>join()</code> or <code>get()</code> parks a thread: ask which one.</li>
<li><strong>What are the limits?</strong> The size of <code>ioPool</code> and its queue, the pricing client's connection pool, the database pool. The smallest one decides how many of these can really run at once.</li>
</ol>

<aside class="callout why">
<p class="callout-title">Why it matters</p>
<p>A chain is a recipe for overlapping waits without dedicating a thread to each wait. That is how the 400 ms page from Chapter 3 becomes 200 ms. Once you can name the thread for every line, the scary-looking code turns into a list of "start this, then when it's done, do that".</p>
</aside>

<aside class="callout recap">
<p class="callout-title">Recap</p>
<ol>
<li>A <code>CompletableFuture</code> is a box that fills later with a value or an error; each chained step makes a new box.</li>
<li><code>thenApply</code> for plain values, <code>thenCompose</code> for async calls, <code>thenCombine</code> / <code>allOf</code> to wait for several, <code>exceptionally</code> / <code>handle</code> for errors.</li>
<li>Always pass your own executor. Without one you share the small common pool with the whole JVM.</li>
</ol>
</aside>
